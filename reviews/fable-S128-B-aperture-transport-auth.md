Verdict: This is an unusually strong sprint spec — the reuse discipline around `ChatSseState`/`on_delta` is exemplary — but it contains three genuine cross-item contradictions (cancellation vs. multi-subscriber broadcast vs. resume; tool/thinking events with no permitted emission point; the `chord.rs`-unmodified gate vs. cancellation plumbing) that would send implementing agents in circles. Fix those and this is approvable.

## ENHANCEMENTS

1. **Reconcile disconnect-cancellation with resume via a grace window and subscriber refcount** — APTR-18. As written, client disconnect trips the cancellation token, but APTR-16 exists precisely so a flaky mobile client can drop and resume mid-turn, and APTR-26 allows multiple subscribers per turn. Specify: generation cancels only when the *last* subscriber disconnects **and** a configurable resume-grace window (named key, aligned with the replay-buffer retention window) expires without a reconnect; explicit stop and revocation cancel immediately regardless of subscriber count. Add tests for: one of two devices disconnects → generation continues; sole device disconnects and resumes within grace → no cancellation, no gap. **P1**
2. **Specify the emission source for `tool.call`, `tool.result`, `thinking`, and `message.start`** — APTR-15/APTR-26. `on_delta` carries text deltas only, and APTR-26 forbids "a new incremental-output hook" — so as written, four of the ten contracted event types have no lawful producer. Name the mechanism explicitly: e.g., a per-turn event emitter handle threaded through `MessageContext`, published from the agent loop's existing tool-dispatch and turn-lifecycle boundaries (which are aggregate-level, not token-level, so the "no new token hook" rule survives). State exactly which agent-loop seams may be touched. **P1**
3. **Bootstrap requires an out-of-band token** — APTR-20. The current design is first-visitor-wins: anyone who reaches an unconfigured instance before the operator becomes admin. Print a one-time high-entropy bootstrap token to the server console/log at startup (or accept it via a CLI subcommand) and require it on the bootstrap-complete call. This closes the deploy-to-bootstrap race and costs the legitimate operator one paste. **P1**
4. **Idempotency key on the message POST** — NEW ITEM (attaches to the REST send path APTR-26 consumes). A client retrying a send after a network blip will double-submit the user's message and trigger two generations. Require a client-generated idempotency key (the existing `request_id` is the natural candidate — say so normatively); the BFF deduplicates within a bounded window and returns the original turn's `stream_id`. Test: duplicate POST yields one `ChannelMessage`, one generation. **P1**
5. **Solve the browser six-connection SSE limit** — APTR-19, NEW work. On HTTP/1.1 a browser caps ~6 connections per origin; a user with several tabs plus the stream plus REST traffic will wedge. Either share one stream across tabs via a `SharedWorker` (with `BroadcastChannel` fan-out and leader election on worker death) or document HTTP/2 as a hard deployment requirement and assert it at startup. Pick one now; retrofitting tab-sharing later touches every consumer. **P1**
6. **Trusted-proxy configuration for the per-source rate-limit dimension** — APTR-24. Behind the reverse proxy every request shares one peer address, so per-source limiting is either useless (all users share one bucket) or spoofable (if `X-Forwarded-For` is trusted blindly). Add a named config key listing trusted proxy hops; derive source identity from the rightmost untrusted-adjacent XFF entry; test both the spoofing attempt and the shared-household case. **P1**
7. **Add a password-change and admin-reset item** — NEW ITEM. APTR-24 rate-limits "password change," but no item in the sprint builds it, and there is no recovery path for a member who forgets a password (admin-initiated reset that invalidates all sessions and forces a new-password flow). Change must require the current password and revoke all *other* sessions of that user. **P1**
8. **Absolute session lifetime cap** — APTR-21. Rotating refresh tokens with no ceiling means a stolen refresh chain lives forever if the victim's device goes quiet. Add a named max-session-age key; past it, refresh fails closed to re-auth regardless of rotation. Test at the boundary. **P2**
9. **`message.end` carries the canonical message id, byte length, and a content hash** — APTR-15/19. This lets the client verify its assembled delta concatenation matches what the server persisted, converting silent delta loss (the transport's worst latent bug) into a detected `gap` and a REST refetch. Cheap to emit, and it turns APTR-19's "identical final state" property into a runtime invariant, not just a test-time one. **P2**
10. **New-device login knock through the assistant's presence budget** — APTR-23, Soul Contract clause 2. When a session is issued for a previously unseen device, the assistant (not a system tray) tells the user on their other surfaces: "someone just signed in from a new desktop — you?" with a one-tap `revoke` action. This is the lost-phone story made proactive, uses the sanctioned presence channel, and is exactly the assistant-operable framing the Module Contract wants. **P2**
11. **Security-events surface in settings** — APTR-23/24. Show the user their recent logins, refresh-reuse alarms, lockouts, and revocations (the audit events these items already generate), per-user-scoped. A sovereign instance's user has nowhere else to look. **P2**
12. **Replay buffer stores post-sanitization events only** — APTR-16. Make it an explicit invariant with a test that the APTR-10 sanitizer runs *before* buffering, so a resume replay can never emit a pre-redaction tool result that the live path would have redacted. As written the ordering is unstated. **P2**
13. **Enumerate the in-stream `error` class taxonomy in the errors contract** — APTR-15/17/18/23 all mint error classes ("upstream-timeout," "rate/backpressure," "typed auth error") informally. Freeze the class list in `contracts/aperture-errors-v1.md` with client-behavior guidance per class (retry / re-auth / refetch / give up), and add the contract-enum drift test the event taxonomy already has. **P2**
14. **Property test: disconnect at every event boundary** — APTR-19. Upgrade the single "disconnect mid-turn" integration test to a property test that severs and resumes the stream at *every* event boundary (and mid-frame) of a scripted turn, asserting the reduced state equals the uninterrupted run each time. This is the test that actually catches off-by-one resume bugs; one sample point will not. **P2**
15. **`__Host-` cookie prefix** — APTR-21. Name the session cookie with the `__Host-` prefix so the browser itself enforces `Secure`, no `Domain`, and `Path=/` — defense in depth against a misconfigured deploy, for free. **P2**
16. **Explicit Origin check on the SSE GET plus a deny-all CORS posture** — APTR-21/15. The spec says "session binding verified per connection" but should also mandate: reject any stream or state-changing request whose `Origin`/`Sec-Fetch-Site` indicates cross-site, and ship no CORS headers at all (same-origin only, stated in the contract). Add the negative test: a cross-origin EventSource/fetch is refused even with a valid cookie. **P2**
17. **Session-id regeneration at the auth boundary** — APTR-20/21. State explicitly that any pre-authentication cookie or identifier (bootstrap state, CSRF token, anonymous session if one ever exists) is discarded and reissued on successful login, with a test — this is the session-fixation clause the sprint currently addresses only implicitly. **P2**
18. **Telegram enablement consent interstitial** — APTR-27. Enabling Telegram routes conversation content through a third party — a real sovereignty exception. The enable flow should present the privacy posture (what leaves the boundary, what Telegram sees) and require explicit confirmation; the doc alone will not be read at the moment of decision. **P2**
19. **Admin operational counters behind the admin guard** — NEW ITEM. Active stream count, per-user cap hits, limiter trips, replay-gap emissions, slow-consumer evictions — exposed on an authenticated admin route (and assistant-queryable, per clause 4). Zero telemetry leaves the box; without this, APTR-17/24's tuning knobs are tuned blind. **P2**
20. **Server-assigned per-thread message index for read positions** — APTR-25. "Highest-read message position" needs a total order that all devices agree on; client-observed order or timestamps won't survive edits/compaction. Mandate a server-assigned monotonic per-thread index as the position domain and say so in the contract. **P2**
21. **Chaos harness for the full SSE path** — NEW ITEM, Sprint B deliverable reused in G. An in-process flaky-proxy (injected latency, mid-frame cuts, byte-level buffering) wrapped around the stream endpoint, driving APTR-15/16/17/19 together. The individual items test their own seams; nothing tests the composition, which is where SSE stacks actually fail. **P2**
22. **WebAuthn/passkeys as a login method** — APTR-21, NEW work. For a self-hosted instance, passkeys are strictly better than passwords (phishing-resistant, nothing to rate-limit, nothing to hash) and the device-registry item already gives you the credential-per-device model. Even shipping it as the *second* method in this sprint changes the product's security ceiling. **P2**
23. **TOTP second factor** — APTR-21. Bundled, offline, no external dependency; enrollment QR rendered locally. Lower priority if passkeys land. **P3**
24. **QR-code device linking** — APTR-23. Log in on a phone by scanning a short-lived, single-use code displayed by an authenticated desktop session — the delightful multi-device onboarding for a PWA, and it reuses the invite-token machinery (hashed at rest, expiring, single-use). **P3**
25. **Own the `retry:` field and the EventSource auto-reconnect decision in the contract** — APTR-19 lists "disable the built-in or own it explicitly" as an edge case; promote it to a contract decision (recommend: fetch-reader path everywhere, built-in reconnect disabled) so two implementers don't choose differently. **P3**
26. **Document and test SSE vs. compression/buffering middleware** — APTR-15. Any gzip/brotli layer in `lumina-core`'s router or the reverse proxy will re-buffer the stream and defeat the padding trick. Explicitly exempt `text/event-stream` from compression and add an integration test asserting first-byte delta latency under the deployed middleware stack. **P3**
27. **Invite links as deep links with QR rendering** — APTR-22, pairing with Sprint E/F deep-link work. The admin gets a copyable URL and a QR, not a bare token to dictate over the phone. **P3**
28. **Terminal `usage` metadata on `message.end`** — APTR-15. Duration and token counts (numbers only — no model, engine, or proxy-tier detail beyond the named proxy) so Sprint C can render "this turn took 12s / 1.4k tokens" and the operator can see cost. **P3**

## DEFECTS

- **APTR-18 × APTR-16 × APTR-26 — cancellation contradicts resume and multi-subscriber broadcast.** APTR-18 cancels on client disconnect (proactively, via the closed signal); APTR-16 exists so a dropped client can resume the same turn; APTR-26 allows two devices subscribed to one turn. All three cannot hold as written — the first disconnect would kill generation for the surviving device and make resume-after-drop resume a *cancelled* turn every time. Needs the refcount + grace-window model (Enhancement 1) written into all three items before any agent implements them.
- **APTR-15/APTR-26 — four contracted event types have no permitted producer.** The only sanctioned wiring is the `on_delta` text callback, and APTR-26 forbids new agent-loop hooks, yet the taxonomy requires `tool.call`, `tool.result`, `thinking`, and lifecycle events that `on_delta` cannot carry. The prohibition and the taxonomy are in direct conflict; see Enhancement 2.
- **APTR-26 vs. APTR-18 — the `chord.rs`-unmodified grep gate is likely unsatisfiable.** APTR-18 requires cancellation to reach `chat_completion_streaming` and "stop the body read," which almost certainly means adding a cancellation token parameter to `chord.rs`. APTR-26's acceptance criterion "`chord.rs` unmodified" will fail once APTR-18 merges (or force APTR-18 into a hack). Sequence and scope the two explicitly.
- **APTR-20/APTR-22 — audit logging is cited as "(APTR-24)" but APTR-24 defines no audit log.** APTR-24 only specifies *rate-limited* abuse logging. No item in the sprint defines the audit sink, schema, or retention that APTR-20/22/23 all depend on. Either point at the existing agent-core audit log by module path or add the item.
- **APTR-24 — per-source limiting is undefined behind the reverse proxy.** Without a trusted-proxy specification the "coarse network identity" is either one shared bucket for all users or attacker-spoofable via `X-Forwarded-For` (Enhancement 6). As written the dimension does not do what the item claims.
- **APTR-16/APTR-19 — "refetch the turn via REST" depends on Sprint C routes.** The gap-recovery contract references a message/turn REST fetch that does not exist until APTR-29+. Either a minimal turn-fetch route belongs in Sprint B or the gap contract must state that recovery is deferred (and the APTR-19 gap test must not depend on it).
- **APTR-15/16 — `stream_id` lifecycle is never defined.** Is a stream one connection, one thread, or one turn? Resume semantics, the replay buffer, the per-user cap, and the reducer all key off it, and each item is readable under a different interpretation. Pin it in `aperture-events-v1.md` (recommend: one stream per connection, `thread_id`/message id doing the demultiplexing — which the event fields already support).
- **APTR-15 — the `thinking` opt-in mechanism is unspecified.** "Opt-in per thread" names no route, query parameter, or thread setting, so the acceptance criterion "opt-in and off by default" is not testable as written.
- **APTR-20 — first-visitor-wins bootstrap** (see Enhancement 3). The transactional race guard protects against *concurrent* attackers but not against whoever arrives first; on a network-exposed instance that is the actual threat.

## MISSING

- **Password change and recovery** — referenced by APTR-24, built by nobody (Enhancement 7).
- **Audit log definition** — sink, schema, per-user visibility, retention (Defect above, Enhancements 11).
- **Account lifecycle beyond creation** — deactivation/deletion of a member, and what happens to their threads, devices, sessions, and read state. Even "explicitly deferred to Sprint C, sessions revoked immediately on deactivation" would do; today an admin can invite but never remove.
- **Deployment/TLS posture doc** — `Secure` cookies and Web Push (Sprint F) require HTTPS; nothing states the reverse-proxy/TLS assumptions, the trusted-proxy hops (Defect above), or the HTTP/2 requirement if Enhancement 5 goes that way.
- **Prompt-injection provenance guarantee at the transport layer** — Sprint C will render these events, but Sprint B should already state the invariant: a `tool.result` payload can never be emitted as, or coalesced into, a `token`/assistant event, no matter what bytes the tool returns, with a negative test (a tool result containing SSE-frame-shaped or assistant-event-shaped JSON stays inert data). The reducer's slice separation (APTR-19 §6) implies it; make it contractual.
- **Cross-tab coordination** — beyond the connection limit (Enhancement 5): two tabs both refreshing tokens, both reconnecting, both writing read positions. A leader-election or shared-worker story prevents a family of racy bugs the individual items only patch (the refresh-grace edge case in APTR-21 is a symptom).
- **Operational visibility** — no counters, no admin surface for the limiter/stream registry this sprint creates (Enhancement 19).
- **Time-skew and clock discipline doc** — three items independently invent clock rules (monotonic limiter windows, seq-not-ts resume, leeway on token verification); a single short "clocks in Aperture" contract section would prevent the fourth item from getting it wrong.

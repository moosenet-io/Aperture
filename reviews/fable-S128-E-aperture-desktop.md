Verdict: Strong, unusually security-literate sprint spec — but it hides three real architectural contradictions (bundle identity vs. platform adapter, "Rust holds the token" vs. "the webview makes the requests", updater-launches-installer vs. "no shell capability"), and the update distribution path to self-hosted backends is unspecified. Fix those; the enhancement list below is the main deliverable.

## ENHANCEMENTS

1. **Decide the desktop network topology explicitly — Rust proxy or webview-direct** (APTR-64 / APTR-65, P1). APTR-64 step 6 says the Rust side attaches credentials to outbound requests; APTR-65 says `connect-src` includes the configured endpoint so the webview can reach it. These imply two different architectures. Pick one and specify it: either (a) all REST+SSE traffic goes through Rust commands / a localhost loopback proxy owned by the host process, the webview never holds a token, and `connect-src` is `'self'` only; or (b) the webview talks to the endpoint directly with a short-lived access token and Rust holds only the refresh token. The "if impractical, say so in the PR body" escape hatch is exactly the quiet downgrade the spec elsewhere forbids. Option (a) also solves the "one SSE connection across N windows" requirement for free.

2. **User-provided CA trust for self-hosted endpoints** (APTR-63, P1). The spec rightly bans "continue anyway" on certificate errors — but the target audience is self-hosters, many of whom run a private CA or step-CA on their LAN. Without a sanctioned path, users will terminate TLS badly or give up. Add: import a specific CA certificate (or pin a leaf SPKI hash) per endpoint profile, shown with fingerprint at configure time, stored with the profile, never a global "disable verification" switch. This is the difference between "secure by refusal" and "secure and usable".

3. **Specify how release artifacts reach the user's backend** (APTR-71, NEW ITEM, P1). The feed is served by the user's own BFF — good — but the spec never says how the signed manifest and artifacts get from `release-publish.yml` to an arbitrary user's `lumina-core`. Add an item: the backend periodically pulls (or the operator pushes) a signed release bundle from the public mirror's release page, verifies the manifest signature server-side before serving it, and caches it locally. Without this, APTR-71 is testable only against the operator's own deployment.

4. **Global quick-ask hotkey with a compact assistant popover** (NEW ITEM, P1). The single feature that makes a resident desktop assistant *lived with* rather than *visited*: a global accelerator (configurable, default e.g. Cmd/Ctrl+Shift+Space) that raises a small always-on-top input over any app, sends to the current thread or a scratch thread, and streams the reply inline. Register it through the APTR-66 action registry so it's assistant-visible, and make it a capability (global shortcuts can fail to register). This is the missing obviously-essential feature of the sprint.

5. **Command palette on desktop, wired to native accelerator** (attach to APTR-66, P2). If Sprint C shipped a palette, bind it here (Cmd/Ctrl+K) and extend it with desktop-only entries from the action registry (switch profile, toggle quiet hours, check for updates, open window). If Sprint C did not ship one, that's a Sprint C gap this sprint should surface.

6. **Biometric re-unlock: Touch ID / Windows Hello gating credential release** (attach to APTR-64, P2). The keychain item can require user-presence (macOS `kSecAccessControlUserPresence`, Windows Hello via Credential Guard-adjacent APIs). Offer an opt-in "require biometric to unlock Aperture after idle/lock" that gates the Rust side's use of the stored token. Cheap on top of the existing abstraction, and a real differentiator for a device that holds a lifelong AI relationship.

7. **OS Focus/Do-Not-Disturb state as an input to the presence transport** (attach to APTR-68, P2). The edge case list mentions macOS Focus suppressing delivery; go further — read the OS DND state where the platform exposes it and report it upstream as a context-bus event so the *assistant's budget* knows the user is heads-down, rather than spending knocks into a void. One-way (OS→assistant), opt-in, no override of local quiet hours.

8. **Dock/taskbar badge policy** (attach to APTR-68, P1 as a *rule*, P3 as a feature). Unread badges are notifications by another name. Either declare "no badge, ever" in the spec, or define the badge as budget-governed (set only by a `presence` event, cleared on read). Right now nothing stops a later item adding `setBadgeCount(unread)` — which would be a second knock channel around the Soul Contract. Add it to the single-sink lint's scope.

9. **Taskbar/dock progress for long-running operations** (NEW ITEM, P3). Harmony build runs and Muse acquisitions are exactly what Windows taskbar progress and the macOS dock progress bar exist for. Expose via the platform interface as a capability; drive only from context-bus events the user initiated (no knock budget involved — it's a status surface, not a notification).

10. **Update release notes are untrusted content — sanitize** (attach to APTR-71, P1). The manifest carries a "release notes reference" that will be rendered in the update UI inside the privileged shell. State explicitly that release notes render through the same sanitized markdown pipeline as chat (no raw HTML, no inline handlers), because a compromised backend serving a manifest is precisely the threat the signature scheme addresses — signed notes should still never be rendered as HTML.

11. **Delta/patch updates** (attach to APTR-71, P3). Tauri artifacts are small, but a binary-diff layer (e.g. zstd-dictionary or bsdiff over the payload) keeps updates in the low single-digit MB for self-hosters on slow uplinks. Manifest gains an optional `delta_from` entry; full artifact remains the fallback; verification still runs on the *reconstructed* artifact digest.

12. **Enterprise/managed endpoint pre-provisioning for the MSI** (attach to APTR-69, P2). "No hardcoded server, ever" is a ship-time rule, not a deployment rule. Add a documented MSI property / registry policy key (`APERTURE_MANAGED_ENDPOINT`) an administrator can set, which pre-fills (and optionally locks) the endpoint profile. Without it, the per-machine MSI story ("managed deployment") is incoherent — an admin deploys to 50 machines and every user still types a URL.

13. **macOS uninstall story** (attach to APTR-70, P2). Windows gets a careful uninstaller; macOS gets drag-to-trash, which orphans keychain items, `~/Library/Application Support`, the launch-at-login agent, and update staging. Add an in-app "Remove Aperture from this Mac…" action (or a documented `--uninstall` flag) that enumerates and removes exactly what APTR-64/66/71 wrote, mirroring the Windows "remove my data" semantics.

14. **Resolve the updater-vs-capability conflict** (attach to APTR-65 + APTR-71, P1). APTR-65 says "no `shell` execute capability at all"; APTR-71's Windows apply path must launch the NSIS installer, and macOS may need helper execution for the atomic swap. Specify the sanctioned mechanism: a single Rust-side `apply_verified_update()` that spawns only the just-verified, digest-pinned staged artifact by absolute staged path — not a webview-reachable command, not a general spawn. The posture test should assert the spawn site is unreachable from IPC and only accepts the staged, verified path.

15. **Fix the bundle-identity contradiction with a two-artifact rule** (attach to APTR-61, P1). "Byte-identical bundle" and "build:desktop registers the desktop adapter at build time" cannot both be true. Specify: one shared bundle byte-identical across targets, plus a tiny target-specific *loader* (adapter registration + entry flag) that is the only file allowed to differ, and the hash comparison covers everything except that enumerated loader. As written, the acceptance test either fails forever or gets quietly weakened.

16. **State the `connect-src` mechanism concretely** (attach to APTR-65, P1). "Injected at runtime from the connection manager… re-applied on profile switch" hand-waves a hard problem: WKWebView/WebView2 CSP comes from the served document or config, and changing it means regenerating the header and reloading the webview. Specify the mechanism (custom protocol handler serving `index.html` with a generated CSP header; profile switch forces a controlled reload) and add a test that the post-switch webview cannot reach the *previous* profile's origin. (Moot if enhancement #1 lands as the proxy option — prefer that.)

17. **Draft durability across update-restart and crash** (attach to APTR-63/71, P2). Drafts are mentioned twice ("preserve drafts" on upgrade) but never given a home. Specify: drafts persist to local app-data (they are user content, not credentials), survive crash/update/restart, are per-thread, and are included in the "what uninstall's 'remove my data' deletes" enumeration. Add the negative test: kill the process mid-composition, relaunch, draft intact.

18. **Pre-auth probe response must be minimal** (attach to APTR-63, P2). The probe "shows server name, version, available modules" *before* authentication. That's an unauthenticated fingerprinting endpoint on every deployment — exactly the "leak infrastructure detail" class the epic bans. Specify: pre-auth descriptor is product name + API contract version + a deployment-chosen display name only; module list and backend version come post-auth. Add a negative test that the unauthenticated descriptor contains no version/module/infra fields.

19. **SSE resume semantics on sleep/wake** (attach to APTR-63, P2). Laptops sleep for hours; the spec says "treat wake as `reconnecting`" but not what happens to the event gap. Specify Last-Event-ID resume against the Sprint B stream, a bounded server replay window, and the client behavior when the gap exceeds the window (full thread refetch, with presence events *not* re-knocked — ties into APTR-68's dedupe). Test: sleep past the replay window, wake, no duplicate messages, no phantom knocks.

20. **Local diagnostics bundle instead of crash reporting** (NEW ITEM, P2). Sovereignty forbids crash upload — good — but users will still hit crashes and need to report them *by hand*. Add "Save diagnostics…": redacted logs (endpoint reduced to scheme+host-shape, zero tokens — reuse the APTR-63 redactor), version, OS, capability states, last N state-machine transitions, written to a user-chosen path via the save dialog. Include a test that greps the produced bundle for token/endpoint values.

21. **Log hygiene as its own enforced surface** (NEW ITEM, P2). Several items say "logged locally at debug level" but nothing owns rotation, size caps, location, or the redaction guarantee across *all* crates. One item: a single `tracing` subscriber in the host with a redacting layer, bounded rotating files in app-data, and a CI test that the log output of an integration run contains no secret-shaped or endpoint-literal strings. Without it, ten items each log "carefully" and one of them doesn't.

22. **Muse mini-player / picture-in-picture window** (NEW ITEM, P3). APTR-61 already names "a Muse player" as a detached window; make it delightful: a frameless, always-on-top mini-player with media-key integration (play/pause/next via the OS media session APIs), registered as actions in APTR-66's registry so the assistant can also drive it. Media keys are the canonical "feels native" test users apply on day one.

23. **"Show the becoming" gets a desktop presence** (attach to APTR-66, P3). Soul Contract clause 3 requires trait drift and revised opinions on a first-class surface. On desktop, add a tray-menu entry ("What's changed in Lumina") deep-linking (via APTR-67) to that surface, and let a budgeted presence event of the `becoming` category light a subtle tray-icon state (not a notification). Cheap, and it makes the contract clause visible daily instead of once.

24. **E2E harness for the desktop shell in CI** (attach to Sprint G but wire here, P2). The test plans lean on unit + "integration on a clean VM" without naming the driver. Specify `tauri-driver`/WebDriver-based e2e running on both packaging hosts for the critical paths: first-run flow, offline transition, deep-link cold/warm, notification activation, update-and-rollback. Otherwise half the acceptance criteria in this sprint are manually verified once and never again.

25. **Deep-link "copy link" affordance + link grammar published to the assistant** (attach to APTR-67, P3). Registration and validation are covered; generation isn't. Add a "Copy link to this thread/run/item" action (registry-backed), and publish the link grammar as a Terminus-visible schema so the assistant can *emit* valid deep links in its own replies instead of guessing the scheme from config it can't see.

26. **Screen-share privacy mode** (NEW ITEM, P3). A one-toggle "privacy mode" (tray + palette) that blurs message bodies and suppresses notification content — the desktop analogue of APTR-68's lock-screen setting. People screen-share all day; a personal AI's transcript is the worst thing to leak on a call.

## DEFECTS

- **APTR-61 vs APTR-61 test plan**: "byte-identical bundle" acceptance criterion contradicts "`build:desktop` emits the same bundle with the desktop platform adapter registered" via a build-time flag. As written the hash test cannot pass, or the adapter registration cannot be build-time. Needs the two-artifact rule (Enhancement 15).
- **APTR-64 step 6 vs APTR-65 CSP**: "Rust attaches credentials to outbound requests" and "`connect-src` includes the configured endpoint" describe incompatible topologies, and the "say so in the PR body" clause is an unbounded downgrade path in a Critical security item. The topology must be decided in the spec, not by the implementing agent (Enhancement 1).
- **APTR-65 vs APTR-71**: "no `shell` execute capability at all" conflicts with the Windows updater's need to run the NSIS installer. No sanctioned spawn path is specified, so the implementing agent will either violate APTR-65 or block APTR-71 (Enhancement 14).
- **APTR-65 step 7**: "assert the effective CSP at startup and refuse to start" — the effective CSP of a platform webview is not generally introspectable at runtime; as written this posture assertion is not implementable and will be quietly weakened to "assert the config file", which is a different (weaker) guarantee. Specify the actual mechanism.
- **APTR-71 FILES**: the BFF update-feed route is a "sibling PR in the agent-core repo" — a cross-repo dependency with no item, no owner, no acceptance criteria, and no statement of how artifacts reach arbitrary self-hosted backends. The sprint's Critical item depends on unscheduled work (Enhancement 3).
- **APTR-63 probe**: pre-auth exposure of server version and module list contradicts the epic's "never leak infrastructure detail" requirement (Enhancement 18).
- **APTR-68 FILES**: the single-sink enforcement is `lint-notification-sink.mjs` (a Node script) but the sink and any bypass risk live in the Rust crate; a JS lint cannot see Rust call sites. The enforcement must be the Rust architectural test, with the .mjs lint covering only the TS side — as written the named enforcement tool cannot enforce the named property.
- **APTR-70 / APTR-71**: "atomic swap preserving the quarantine/stapling state" — a self-applied update is not quarantined, and stapling belongs to the *new* bundle fetched from the feed; "preserving" the old bundle's state is a category error. Specify: the staged bundle ships stapled, and the swap must not strip its ticket.

## MISSING

- **Linux desktop**: the fleet is Rust-first and self-hosted — the archetypal user runs Linux. Even if deliberately out of scope, the spec should say so and confirm APTR-62's abstraction doesn't bake in a two-OS assumption (e.g., tray semantics).
- **Private-CA / certificate-pinning path** for self-hosted TLS (the #1 real-world first-run failure for this audience).
- **Artifact distribution to user backends** — the entire supply path between the release job and the sovereign update feed.
- **Draft persistence design** — referenced by three items, owned by none.
- **Log lifecycle** — rotation, caps, location, and a cross-crate redaction guarantee.
- **Uninstall on macOS** and any statement of what "remove my data" means there.
- **E2E driver/harness** for desktop-specific flows; without it most acceptance criteria are one-time manual checks.
- **Badge/dock-bounce/attention-request policy** — currently an unregulated second presence channel.
- **Proxy environments** (corporate HTTP proxies, PAC) — decide support or explicit non-support; silent failure here looks like "backend down".
- **Migration**: a user moving from web-only (Sprint C) to desktop — does the desktop first-run offer to adopt the existing session/device, or is it always a new device pairing? Unstated, and it's the very first thing the operator will do.
- **Idle/lock behavior**: whether the in-memory credential (APTR-64 fallback mode) survives OS lock/sleep, and any auto-lock of the app itself.
- **Accessibility of the native surfaces** (tray, menus, notifications, first-run) — Sprint G covers the web bundle; nothing covers the Rust-owned chrome.
